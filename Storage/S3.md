## 1. What is S3?

Amazon S3 (Simple Storage Service) is a scalable, secure, and durable **object storage** service offered by AWS. It stores and retrieves any amount of data from anywhere on the web.

- **Durability**: 99.999999999% (11 nines) — achieved by redundantly storing data across a minimum of 3 Availability Zones.
- **Availability**: 99.99% (varies by storage class).
- **Scalability**: No practical limit on total storage; a single object can be up to 5 TB.
- **Use cases**: Backup & restore, static website hosting, data lakes, big data analytics, media storage/distribution, disaster recovery, archiving.

## 2. Buckets and Objects

In Amazon S3, the two fundamental components are **buckets** and **objects**.

### Buckets

A **bucket** is a container for storing objects in S3.

**Key characteristics:**
- Created in a specific **AWS Region**.
- Bucket names must be **globally unique** (across all AWS accounts, not just your own).
- A single AWS account can have up to 100 buckets by default (soft limit, extendable to 1,000+ via a quota increase request).
- You can configure:
  - **Permissions** (IAM, bucket policies, ACLs)
  - **Versioning**
  - **Lifecycle rules**
  - **Logging**
  - **Encryption**
  - **Object Lock / retention**
  - **Static website hosting**

### Objects

An **object** is the actual data stored in a bucket.

**Each object consists of:**
1. **Data** — the file content (max object size: 5 TB; single PUT max: 5 GB, above which multipart upload is required).
2. **Key** — the unique identifier within the bucket (S3 is a flat namespace; "folders" are just key prefixes, e.g. `images/2024/photo.jpg`).
3. **Metadata** — system metadata (content type, size) and custom user metadata (`x-amz-meta-*` headers).
4. **Version ID** — assigned if versioning is enabled.

### Relationship

- A **bucket** can contain **unlimited objects**.
- Each object is uniquely identified by its **key** within the bucket.
- Region + bucket name + key = a unique, addressable resource in S3.

## 3. S3 Storage Classes

| Storage Class | Use Case | Retrieval Time | Recommended Usage Period | Min Storage Duration | Availability | Cost |
|---|---|---|---|---|---|---|
| **S3 Standard** | Frequently accessed data | Milliseconds | Minutes to daily access | None | 99.99% | High |
| **S3 Intelligent-Tiering** | Unpredictable access patterns | Milliseconds | Minutes to monthly access | None | 99.9% | Adaptive (small monitoring fee) |
| **S3 Standard-IA** | Infrequently accessed, but needed quickly | Milliseconds | Days to monthly access | 30 days | 99.9% | Lower (+ retrieval fee) |
| **S3 One Zone-IA** | Non-critical infrequent access (single AZ) | Milliseconds | Days to monthly access | 30 days | 99.5% | Lower still |
| **S3 Glacier Instant Retrieval** | Archived data needing occasional instant access | Milliseconds | Monthly to quarterly access | 90 days | 99.9% | Low |
| **S3 Glacier Flexible Retrieval** | Long-term archives with flexible retrieval | Minutes to hours | Quarterly to yearly access | 90 days | 99.99% | Very Low |
| **S3 Glacier Deep Archive** | Compliance or rarely accessed long-term backups | Hours (12h standard) | Yearly or longer | 180 days | 99.99% | Lowest |

#### Quick Decision Guide
- **Need fast, frequent access?** → Standard or Intelligent-Tiering
- **Access pattern unknown/changing?** → Intelligent-Tiering
- **Access once a month, need it fast?** → Standard-IA
- **Same as above but okay losing an AZ?** → One Zone-IA
- **Archive but need instant access sometimes?** → Glacier Instant Retrieval
- **Archive with flexible access (minutes–hours ok)?** → Glacier Flexible Retrieval
- **Rarely accessed, long-term compliance storage?** → Glacier Deep Archive

> **Interview tip:** IA and Glacier classes charge an **early deletion fee** if you delete/transition an object before its minimum storage duration, and a **per-GB retrieval fee** for IA/Glacier — this is a common "gotcha" question.

## 4. Data Consistency Model

| Operation | Consistency Behavior |
|---|---|
| **PUT (Create/Update)** | Strongly consistent — immediately visible after success (read-after-write). |
| **DELETE** | Immediately removed; a subsequent GET/LIST will not return the object. |
| **LIST** | Immediately reflects changes (new objects appear, deleted ones disappear). |
| **GET** | Always returns the latest version of the object. |
| **HEAD** | Consistent with GET; reflects latest metadata. |
| **COPY** | Strongly consistent; copied object is immediately available. |
| **MULTIPART UPLOAD** | Finalized object is immediately available after `CompleteMultipartUpload`. |

#### What Strong Consistency Means
- Since **December 2020**, S3 provides strong read-after-write consistency for **all** operations (PUTS of new objects, overwrite PUTS, and DELETES) — no configuration needed.
- You don't need retry logic or delays to ensure visibility of changes.
- Simplifies application logic, especially for distributed systems (previously S3 only offered *eventual* consistency for overwrite PUT/DELETE — this is a common outdated interview trap).

## 5. Bucket Policies

A **bucket policy** is a resource-based JSON IAM policy attached directly to a bucket that defines who can access the bucket/objects and what actions they can perform.

### Structure

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadFromSpecificAccount",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" }
      }
    }
  ]
}
```

### Key Concepts
- **Principal**: who the statement applies to (an AWS account, IAM user/role, service, or `*` for everyone).
- **Action**: S3 API actions (`s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:ListBucket`, etc.).
- **Resource**: the bucket ARN (`arn:aws:s3:::bucket`) for bucket-level actions, or `arn:aws:s3:::bucket/*` for object-level actions.
- **Condition**: optional constraints (IP range, VPC endpoint, MFA, SSL-only via `aws:SecureTransport`, etc.).

### Common Use Cases
- Granting **cross-account access** without IAM roles.
- Enforcing **HTTPS-only** access (`"Condition": {"Bool": {"aws:SecureTransport": "false"}}` with `Effect: Deny`).
- Restricting access to a specific **VPC endpoint**.
- Granting **public read** access (e.g., for static website hosting) — requires Block Public Access to be disabled for that setting.
- Denying deletes to protect critical data.

### Bucket Policy vs IAM Policy (Quick View)
| Aspect | Bucket Policy | IAM Policy |
|---|---|---|
| Attached to | The bucket (resource-based) | A user/group/role (identity-based) |
| Best for | Cross-account & public access | Internal, per-user/role access control |
| Max size | 20 KB | 6 KB (user) / 10 KB (role) |

> **Interview tip:** When a bucket policy and an IAM policy both apply, S3 evaluates **all applicable policies together**; an explicit `Deny` in either always wins over any `Allow`.

## 6. IAM Policies for S3

**IAM policies** are identity-based JSON policies attached to IAM users, groups, or roles that define what S3 actions they can perform, on which resources.

### Example

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::my-app-bucket/uploads/*"
    },
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-app-bucket",
      "Condition": { "StringLike": { "s3:prefix": ["uploads/*"] } }
    }
  ]
}
```

### Key Points
- Scoped to a **principal** (user/role), not a resource — the opposite orientation of a bucket policy.
- Supports fine-grained actions: `s3:GetObject`, `s3:PutObjectAcl`, `s3:RestoreObject`, `s3:GetBucketVersioning`, etc.
- Can use **variables** like `${aws:username}` to build per-user folder access (e.g., restrict each user to their own prefix).
- Combine with **conditions** (MFA required, source VPC, tag-based access control) for fine-grained control.
- Access is evaluated using the **union of all applicable policies** (identity-based + resource-based + SCPs + permission boundaries), with an explicit `Deny` overriding everything.

### When to Use IAM vs Bucket Policy
- **IAM policy**: managing access **within your own account**, for many buckets, centrally, per user/role.
- **Bucket policy**: granting access **across accounts**, or public/anonymous access, or when the grantee has no IAM identity in your account.

## 7. Access Control Lists (ACLs)

**Access Control Lists (ACLs)** in Amazon S3 are used to **grant read/write permissions** to buckets and objects. They are one of the two main ways to manage access in S3, the other being **bucket policies** (which are generally preferred).

ACLs are:
- **Attached to each object and bucket**
- **Used to grant access to specific AWS accounts or predefined groups**
- **Less flexible and harder to manage** than bucket policies

### ACL Structure
An ACL consists of:
- **Grantee**: the entity receiving permissions (AWS account, group, or canonical user ID)
- **Permission**: the level of access granted (e.g., `READ`, `WRITE`, `FULL_CONTROL`)

### Common Grantees
- **Canonical User ID**: unique identifier for an AWS account
- **Predefined Groups**:
  - `AllUsers`: public access
  - `AuthenticatedUsers`: any AWS authenticated user

### Permissions
| Permission | Bucket | Object |
|---|---|---|
| `READ` | List objects | Read object data |
| `WRITE` | Add/delete objects | N/A |
| `READ_ACP` | Read ACL | Read ACL |
| `WRITE_ACP` | Write ACL | Write ACL |
| `FULL_CONTROL` | All permissions | All permissions |

### How ACLs Work
- **Bucket ACLs** control access to the bucket itself (e.g., listing contents).
- **Object ACLs** control access to individual objects.
- ACLs are **independent of bucket policies**, but both can apply simultaneously.
- ACLs are **not recommended** for fine-grained access control.
- As of April 2023, new buckets have **ACLs disabled by default** (Object Ownership = "Bucket owner enforced").

### Important Considerations

**1. ACLs vs Bucket Policies**
- Bucket policies are more powerful, scalable, and easier to manage.
- ACLs are legacy and should be avoided unless necessary.

**2. Object Ownership**
- When another AWS account uploads an object to your bucket, they own the object unless you use **bucket owner enforced** settings or **object ownership** settings.

**3. Public Access**
- ACLs can make buckets or objects public if `AllUsers` is granted `READ`.
- AWS now blocks public ACLs by default using **Block Public Access** settings.

**4. Security Risks**
- Misconfigured ACLs can lead to unintended public access.
- Always audit ACLs and apply least-privilege principles.

**5. Programmatic Access**
- Manage ACLs via AWS CLI (`aws s3api put-object-acl`), SDKs, or the Console (limited).

### Best Practices
- Prefer **bucket policies** or **IAM policies** over ACLs.
- Use **Object Ownership settings** to simplify access control.
- Enable **Block Public Access** to prevent accidental exposure.
- Regularly audit ACLs using AWS Config or custom scripts.

### Comparison Table

| Feature / Aspect | IAM Policies | Bucket Policies | ACLs |
|---|---|---|---|
| Scope | AWS user/role level | Bucket level | Bucket & object level |
| Granularity | Fine-grained | Fine-grained | Limited |
| Target Audience | IAM users, roles, federated identities | Any AWS principal or public | Specific AWS accounts or groups |
| Use Case | Centralized access control | Cross-account access, public access | Legacy object-level permissions |
| Ease of Management | High | Moderate | Low |
| Recommended for | Internal access control | External access, public access | Rare legacy scenarios |
| Supports Conditions | ✅ Yes | ✅ Yes | ❌ No |
| Supports Resource Wildcards | ✅ Yes | ✅ Yes | ❌ No |
| Supports Public Access | ❌ No (unless combined with bucket policy) | ✅ Yes | ✅ Yes (via `AllUsers`) |
| Object-Level Control | ✅ Yes (via IAM actions) | ✅ Yes | ✅ Yes |
| Cross-Account Access | ✅ Yes | ✅ Yes | ✅ Yes (limited) |
| Best Practice | ✅ Recommended | ✅ Recommended | ❌ Avoid unless necessary |
| Security Risk | Low (if well-managed) | Medium (if public access misconfigured) | High (easy to misconfigure) |

### Summary
- **IAM Policies** — best for internal access control within your AWS account; centrally managed via IAM; flexible and secure.
- **Bucket Policies** — best for cross-account and public access; applied directly to the bucket; supports conditions and IP restrictions.
- **ACLs** — legacy feature, not recommended for most use cases; used for object-level permissions to specific AWS accounts; error-prone and hard to audit.

## 8. S3 Block Public Access

Amazon S3's **Block Public Access** feature is a security mechanism that prevents accidental exposure of data stored in S3 buckets. It provides account-level and bucket-level settings to restrict public access, regardless of individual object permissions or bucket policies.

### Key Components (4 settings)

1. **Block Public ACLs** — prevents new public ACLs and ignores existing public ACLs on buckets/objects.
2. **Ignore Public ACLs** — ensures any public ACLs are completely disregarded.
3. **Block Public Bucket Policies** — prevents the use of bucket policies that allow public access.
4. **Restrict Public Bucket Policies** — ensures only AWS accounts with specific permissions can apply public bucket policies.

### How to Enable

- **AWS Management Console**: S3 → [Bucket name] → Permissions → Block Public Access.
- **AWS CLI**:
  ```bash
  aws s3api put-bucket-policy --bucket my-bucket-name --policy file://policy.json
  aws s3api put-public-access-block --bucket my-bucket-name \
    --public-access-block-configuration \
    BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
  ```
- **AWS SDKs**: configure programmatically via the relevant SDK.

### Best Practices
- Always enable Block Public Access unless you have a specific, secure use case for public data (e.g., static website hosting).
- Use IAM and bucket policies to manage access securely.
- Regularly audit buckets with AWS Trusted Advisor or S3 Access Analyzer.

## 9. Encryption

S3 supports encryption **at rest** and **in transit**.

### In Transit
- Enforced via **HTTPS/TLS**. Can be required with a bucket policy condition on `aws:SecureTransport`.

### At Rest — Server-Side Encryption (SSE)

| Type | Who manages the key | Notes |
|---|---|---|
| **SSE-S3** | AWS manages the key (AES-256) | Default for new buckets/objects since 2023; simplest option, no extra cost. |
| **SSE-KMS** | AWS KMS-managed customer key (CMK) | Adds auditability (CloudTrail logs key usage), supports key rotation and fine-grained key policies; has KMS request costs/limits. |
| **SSE-C** | Customer-provided key (you supply the key with each request) | AWS never stores the key; you must send it on every GET/PUT; not replicated with SSE-C by default. |

### Client-Side Encryption
- Data is encrypted **before** it's uploaded to S3, by the client application (e.g., AWS Encryption SDK / S3 Encryption Client). S3 stores only ciphertext and never sees the plaintext key.

### Key Points
- Encryption can be enforced via **bucket policy** (deny `PutObject` unless `x-amz-server-side-encryption` is set) or via **default bucket encryption** settings.
- Since January 2023, **SSE-S3 encryption is enabled by default** on all new buckets and objects at no extra cost.
- SSE-KMS is the go-to for compliance-heavy workloads needing audit trails and access control on the key itself, but watch for **KMS request-rate throttling** on high-throughput workloads (mitigated with S3 Bucket Keys).

## 10. VPC Endpoints for S3

A **VPC Endpoint for S3** is a **gateway endpoint** that enables private connectivity between your Amazon VPC and Amazon S3, without using the public internet.

Instead of routing traffic through a NAT gateway or internet gateway, your VPC can access S3 securely and privately using AWS's internal network.

### Benefits
- **Enhanced Security**: no exposure to the public internet.
- **Cost Savings**: avoids NAT gateway data transfer charges.
- **Simplified Architecture**: no need for public IPs or internet gateways.
- **Compliance**: helps meet data residency and security requirements.

### Key Components

| Component | Description |
|---|---|
| **Gateway Endpoint** | A VPC endpoint type used specifically for S3 and DynamoDB (free of charge). |
| **Route Table Entry** | Adds a route to the endpoint in the VPC's route table. |
| **Endpoint Policy** | Controls access to S3 resources via the endpoint. |
| **Private DNS** | Not applicable for S3 gateway endpoints (used for interface endpoints instead). |

### How It Works
1. Create a **Gateway Endpoint** for S3 in your VPC.
2. Attach it to the route tables of subnets that need access.
3. Define an **endpoint policy** to restrict or allow access to specific buckets or actions.
4. Configure bucket policies to allow access **only via the VPC endpoint** (optional but recommended), using `aws:SourceVpce`.

### Security Best Practices
- Use bucket policies to restrict access to requests coming only from your VPC endpoint.
- Use IAM policies and endpoint policies together for layered security.
- Enable logging/monitoring via CloudTrail and VPC Flow Logs.

### Use Cases

| Use Case | Description |
|---|---|
| **Private Data Access** | Access S3 from EC2, Lambda, or ECS without internet exposure. |
| **Secure Data Lake** | Build a secure data lake using S3 and VPC endpoints. |
| **Cost Optimization** | Avoid NAT gateway charges for S3 access. |
| **Compliance** | Meet regulatory requirements for private data access. |
| **Hybrid Architectures** | Connect on-premises systems via Direct Connect to S3 securely. |

> **Note**: There are two types of S3 endpoints — **Gateway endpoints** (free, route-table based, S3/DynamoDB only) and **Interface endpoints** (PrivateLink-based, ENI with a private IP, incur hourly + data charges, needed when accessing S3 from on-premises via Direct Connect/VPN).

## 11. Lifecycle Policies

**S3 Lifecycle** rules automate moving objects between storage classes or deleting them as they age, to optimize cost.

### What a Lifecycle Rule Can Do
1. **Transition actions** — move objects to a cheaper storage class after N days (e.g., Standard → Standard-IA after 30 days → Glacier after 90 days → Deep Archive after 180 days).
2. **Expiration actions** — permanently delete objects after N days.
3. Apply to **current versions**, **noncurrent versions** (in a versioned bucket), **incomplete multipart uploads**, and **expired delete markers**.

### Example

```json
{
  "Rules": [
    {
      "ID": "MoveToIA-ThenGlacier-ThenExpire",
      "Status": "Enabled",
      "Filter": { "Prefix": "logs/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

### Valid Transition Order
Standard → Standard-IA / Intelligent-Tiering → One Zone-IA → Glacier Instant Retrieval → Glacier Flexible Retrieval → Glacier Deep Archive (you cannot transition "backwards" to a cheaper-then-more-expensive-then-cheaper sequence outside this order, and minimum storage durations apply before transitioning further).

### Common Use Cases
- Automatically archive old logs/backups to Glacier.
- Clean up old object versions to control storage bloat (`NoncurrentVersionExpiration`).
- Abort stale/incomplete multipart uploads to avoid being charged for orphaned parts.
- Expire temporary files (e.g., staging/upload buckets).

### Best Practices
- Use **prefix or tag filters** to scope rules to specific data sets.
- Always set `AbortIncompleteMultipartUpload` — a very common cost leak.
- Combine with **Intelligent-Tiering** when access patterns are unpredictable, instead of hand-tuning transition days.
- Test rules on a small prefix before applying account-wide.

## 12. Object Locking and Retention

**S3 Object Lock** provides **WORM (Write Once, Read Many)** protection, preventing objects from being deleted or overwritten for a fixed period or indefinitely — used for regulatory compliance (e.g., SEC 17a-4, FINRA) and ransomware protection.

### Prerequisites
- Object Lock can only be **enabled at bucket creation** (or via AWS Support for existing buckets in limited cases).
- Requires **versioning to be enabled** (Object Lock applies per version).

### Retention Modes

| Mode | Behavior |
|---|---|
| **Governance Mode** | Users can't overwrite/delete objects unless they have special permission (`s3:BypassGovernanceRetention`). Good for internal protection with an "override" escape hatch. |
| **Compliance Mode** | **No one**, including the root account, can delete/overwrite the object until retention expires. Cannot be shortened or removed. Strictest — used for regulatory requirements. |

### Retention Mechanisms
1. **Retention Period** — a fixed date until which the object is protected (`Retain Until Date`).
2. **Legal Hold** — an on/off flag independent of retention period/mode; blocks deletion until explicitly removed, with no expiration date. Requires `s3:PutObjectLegalHold` permission to toggle.

### Key Points
- Applies at the **object version** level, not the whole bucket.
- Cannot be disabled once enabled on a bucket (only individual object retention can, subject to mode rules).
- Often paired with **Compliance mode + MFA Delete** for the highest level of protection (e.g., financial records, audit logs).

## 13. Versioning

Amazon S3 **Versioning** preserves, retrieves, and restores every version of every object in a bucket — useful for data protection, auditing, and recovery from unintended overwrites/deletions.

### What Is Versioning?
When enabled on a bucket:
- Every object gets a unique **version ID**.
- Updates create a **new version**; older versions remain stored.
- Deleting an object adds a **delete marker** but doesn't remove previous versions.

### How to Enable

**AWS CLI:**
```bash
aws s3api put-bucket-versioning \
  --bucket my-bucket-name \
  --versioning-configuration Status=Enabled
```

**AWS Console:** S3 → Bucket → Properties → Bucket Versioning → Enable.

> Once enabled, versioning **cannot be fully disabled** — it can only be **suspended**.

### Object Lifecycle with Versioning

| Action | Result |
|---|---|
| Upload object | Creates a version with a unique ID |
| Overwrite object | New version created; old version retained |
| Delete object | Adds a delete marker (not actual deletion) |
| Delete specific version | Permanently removes that version |
| Delete the delete marker | "Un-deletes" the object (restores prior version as current) |

### Benefits
- **Data Protection**: prevents accidental overwrites/deletions.
- **Recovery**: restore previous versions easily.
- **Audit Trail**: track changes over time.
- **Compliance**: helps meet data retention requirements.

### Managing Versions

Versioning can lead to storage bloat. Use **Lifecycle Policies** to manage it:

```json
{
  "Rules": [
    {
      "ID": "Expire old versions",
      "Status": "Enabled",
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 }
    }
  ]
}
```
This deletes noncurrent versions older than 30 days.

### Considerations
- **Costs**: each version counts toward storage usage.
- **Delete Marker Confusion**: listing objects without version IDs shows only the latest, unless you specify `--version-id`.
- **Replication**: versioning is required for Cross-Region Replication (CRR).

### Useful CLI Commands
```bash
# List versions
aws s3api list-object-versions --bucket my-bucket-name

# Delete a specific version
aws s3api delete-object \
  --bucket my-bucket-name \
  --key my-object-key \
  --version-id version-id
```

## 14. Replication

Amazon S3 Replication automatically and asynchronously copies objects across buckets in the same or different AWS Regions. Commonly used for:
- Disaster recovery
- Compliance requirements
- Data locality / latency reduction
- Backup and archival

### Types of S3 Replication

1. **Cross-Region Replication (CRR)**
   - Replicates objects from a source bucket in one Region to a destination bucket in another.
   - Useful for latency reduction, compliance, disaster recovery.

2. **Same-Region Replication (SRR)**
   - Replicates objects within the same Region.
   - Useful for logging, backup, and data segregation (e.g., across accounts).

### How S3 Replication Works

1. **Enable Versioning** — both source and destination buckets must have versioning enabled.
2. **Set Up Replication Configuration** — define rules specifying:
   - Prefixes/tags to filter which objects to replicate.
   - Destination bucket and IAM role for permissions.
   - Optional replication metrics and notifications.
3. **IAM Role** — AWS uses an IAM role to grant S3 permission to replicate objects on your behalf.
4. **Replication Time Control (RTC)** *(optional)* — guarantees replication within 15 minutes for eligible objects; useful for compliance-sensitive workloads.

### What Gets Replicated?
- New objects created **after** replication is configured.
- Object metadata and ACLs (if configured).
- Delete markers (optional).
- Object tags (if configured).
- Encrypted objects (with proper KMS permissions).

### What Doesn't Get Replicated?
- Objects uploaded **before** replication was enabled (existing objects require **S3 Batch Replication** to backfill).
- Objects encrypted with **SSE-C** (customer-provided keys).
- Delete operations, unless explicitly configured (`DeleteMarkerReplication`).
- By default, replicas are **not further replicated** (no daisy-chaining) unless replica modification sync is set up.

### Monitoring & Auditing
- **CloudWatch Metrics**: track replication status and performance (bytes pending, operations pending, replication latency).
- **Event Notifications**: trigger Lambda/SNS/SQS on replication events.
- **Replication Status**: metadata (`PENDING`, `COMPLETED`, `FAILED`, `REPLICA`) added to objects.

### Security Considerations
- Use bucket policies and IAM roles carefully to control access.
- Ensure KMS permissions are correctly set for encrypted objects.
- Consider data residency laws when replicating across Regions.

## 15. Multipart Uploads

**S3 Multipart Upload** allows uploading a single large object as a **set of parts**, uploaded independently and in parallel, which S3 then assembles into a single object.

### When to Use Multipart Upload

| Condition | Why |
|---|---|
| Object size > 100 MB (recommended) | Improves upload performance and reliability |
| Object size > 5 GB (required) | Multipart upload is **mandatory** for files > 5 GB |
| Need to **resume uploads** after failure | Retry failed parts without re-uploading the whole file |
| Want to **upload in parallel** | Speeds up large uploads using multiple threads/processes |

### When Not to Use Multipart Upload

| Condition | Why |
|---|---|
| Files are small (< 100 MB) | Overhead of managing parts outweighs benefits |
| Don't need parallelism or resumability | Simpler to use a single PUT operation |
| Constrained client environment | Multipart logic adds complexity to client code |

### How It Works (Steps)
1. **Initiate** the multipart upload.
2. **Upload parts** (each part must be 5 MB–5 GB, except the last one; up to 10,000 parts).
3. **Complete** the upload (S3 assembles the parts).
4. Optionally, **abort** the upload if needed.

### S3 Multipart Upload APIs

| API | Purpose |
|---|---|
| `create_multipart_upload` | Initiates a multipart upload and returns an `UploadId`. |
| `upload_part` | Uploads a single part of the file. Requires `PartNumber` and `UploadId`. |
| `upload_part_copy` | Uploads a part by copying data from an existing object. |
| `list_parts` | Lists the parts already uploaded for a specific `UploadId`. |
| `complete_multipart_upload` | Finalizes the upload by assembling all parts into a single object. |
| `abort_multipart_upload` | Cancels the upload and deletes all uploaded parts. |
| `list_multipart_uploads` | Lists all ongoing multipart uploads in a bucket. |

### Typical Workflow
1. **Start**: `create_multipart_upload`
2. **Upload**: `upload_part` (repeat for each part)
3. **Monitor**: `list_parts` or `list_multipart_uploads`
4. **Finish**: `complete_multipart_upload`
5. **Cancel (if needed)**: `abort_multipart_upload`

### Failure Handling & Retry — High-Level Process

**1. Initiate Upload**
- Start with `create_multipart_upload`; save the `UploadId` securely (file or database).

**2. Upload Parts with Retry Logic**
- Split the file into chunks (e.g., 5 MB).
- For each part: try `upload_part`; on failure, retry up to 3 times with exponential backoff; log errors.

**3. Handle Crashes or Interruptions**
- Use the saved `UploadId`.
- Call `list_parts` to see which parts succeeded.
- Resume uploading only the missing parts.

**4. Complete Upload**
- Once all parts are uploaded, call `complete_multipart_upload` with the list of `ETag`s and `PartNumber`s.

**5. Abort if Needed**
- Call `abort_multipart_upload` to clean up and avoid storage charges for orphaned parts.

### Best Practices
- Always **persist `UploadId`** and part metadata.
- Use `list_multipart_uploads` to monitor active uploads.
- Implement logging and alerting for failures.
- Use parallel uploads for performance, but handle retries independently.
- Set a **lifecycle rule** (`AbortIncompleteMultipartUpload`) to auto-clean stale uploads and avoid silent storage charges.

### Reference Implementation (Python / boto3)

```python
import os
import boto3
import logging
import time

logging.basicConfig(level=logging.INFO)

aws_access_key_id = os.getenv('AWS_ACCESS_KEY_ID')
aws_secret_access_key = os.getenv('AWS_SECRET_ACCESS_KEY')
aws_session_token = os.getenv('AWS_SESSION_TOKEN')  # Optional

if not aws_access_key_id or not aws_secret_access_key:
    raise EnvironmentError("AWS credentials not found in environment variables.")

s3 = boto3.client(
    's3',
    aws_access_key_id=aws_access_key_id,
    aws_secret_access_key=aws_secret_access_key,
    aws_session_token=aws_session_token
)

bucket_name = 'your-bucket-name'
file_path = 'your-large-file.zip'
key_name = 'uploads/your-large-file.zip'
chunk_size = 5 * 1024 * 1024  # 5 MB
max_retries = 3

# Step 1: Initiate multipart upload
try:
    response = s3.create_multipart_upload(Bucket=bucket_name, Key=key_name)
    upload_id = response['UploadId']
    logging.info(f"Initiated multipart upload with ID: {upload_id}")
except Exception as e:
    logging.error(f"Failed to initiate multipart upload: {e}")
    raise

# Step 2: Upload parts with retry logic
parts = []
part_number = 1

try:
    with open(file_path, 'rb') as f:
        while True:
            data = f.read(chunk_size)
            if not data:
                break

            for attempt in range(max_retries):
                try:
                    part = s3.upload_part(
                        Bucket=bucket_name,
                        Key=key_name,
                        PartNumber=part_number,
                        UploadId=upload_id,
                        Body=data
                    )
                    parts.append({'ETag': part['ETag'], 'PartNumber': part_number})
                    logging.info(f"Uploaded part {part_number}")
                    break
                except Exception as e:
                    logging.warning(f"Error uploading part {part_number}, attempt {attempt + 1}: {e}")
                    time.sleep(2 ** attempt)
            else:
                raise Exception(f"Failed to upload part {part_number} after {max_retries} attempts.")

            part_number += 1

    # Step 3: Complete multipart upload
    s3.complete_multipart_upload(
        Bucket=bucket_name,
        Key=key_name,
        UploadId=upload_id,
        MultipartUpload={'Parts': parts}
    )
    logging.info("Multipart upload completed successfully.")

except Exception as e:
    logging.error(f"Multipart upload failed: {e}")
    try:
        s3.abort_multipart_upload(Bucket=bucket_name, Key=key_name, UploadId=upload_id)
        logging.info("Multipart upload aborted.")
    except Exception as abort_error:
        logging.error(f"Failed to abort multipart upload: {abort_error}")
```

## 16. Transfer Acceleration

Amazon S3 Transfer Acceleration speeds up uploads (and downloads) to your S3 bucket by routing traffic through the nearest AWS edge location and across Amazon's optimized backbone network. Ideal when clients are geographically far from your bucket's Region and moving large objects — but it adds cost and can underperform for small/local transfers.

### 1. How It Works
- Enable Transfer Acceleration on an S3 bucket.
- Clients use the special accelerate endpoint: `https://<bucket>.s3-accelerate.amazonaws.com`
- Requests go to the nearest CloudFront edge location.
- Data traverses Amazon's private, high-speed backbone into the target Region.
- This typically reduces round-trip latency and boosts throughput versus a direct public-internet path.

### 2. When to Use It
- Users/clients are **≥ 1,000 miles** from the bucket's Region.
- Uploading/downloading **large files** (hundreds of MB to GBs).
- Need **lower latency** and **higher sustained throughput** than the public internet reliably provides.
- Can absorb the additional per-GB acceleration fee for the performance gain.

### 3. When Not to Use It
- Traffic is **local** to the bucket's Region (minimal gain).
- Transferring **small objects** (< 10–50 MB) where TCP handshake/edge hops offset savings.
- Cost is a critical concern — accelerated transfers are billed at an extra per-GB rate.
- Already using a **CloudFront distribution** optimized for downloads (it won't speed up uploads).
- Need guaranteed, ordered delivery at massive scale — acceleration doesn't change S3's delivery semantics.

### 4. Enabling Transfer Acceleration

**AWS Management Console:**
1. Open the S3 console and select your bucket.
2. Go to **Properties** → **Transfer acceleration**.
3. Click **Edit**, choose **Enabled**, then **Save changes**.

### 5. Performance & Cost Considerations

| Factor | Impact |
|---|---|
| Object size | Acceleration shines with large (> 100 MB) transfers |
| Geographic distance | Greater distance ⇒ larger latency reduction |
| Request pattern | Many small PUTs ⇒ edge-hop overhead may negate benefits |
| Pricing | Extra per-GB accelerate fee (~$0.04–0.08/GB, varies by Region) |

> **Tip:** Use the **S3 Transfer Acceleration Speed Comparison tool** in the console to benchmark your exact upload path before rolling it out.

### 6. Alternatives
- **Amazon CloudFront** for accelerated **downloads** and global caching.
- **AWS Snowball Edge** for very large bulk data migrations to AWS.
- **Amazon EventBridge / CloudTrail** for routing S3 API events, not file payloads.

## 17. Event Notifications

S3 Event Notifications let you hook into bucket-level object events (create, delete, restore, replication) and push them to SNS topics, SQS queues, or Lambda functions. Perfect for real-time triggers in decoupled, serverless pipelines, but not the best choice when strict ordering, guaranteed delivery at massive scale, or full audit trails are needed (EventBridge/CloudTrail excel there instead). Configurable via the AWS Console or programmatically via boto3's `put_bucket_notification_configuration`.

### What Are S3 Event Notifications?
S3 Event Notifications emit JSON event records whenever specific object-level actions occur.
- **Supported actions**: `ObjectCreated:*`, `ObjectRemoved:*`, `ObjectRestore:*`, replication events, lifecycle transitions.
- **Destinations**:
  - **Lambda** — immediate, serverless processing.
  - **SQS** — reliable, decoupled queueing and batching.
  - **SNS** — pub/sub fan-out to multiple subscribers.
  - **Amazon EventBridge** — newer, richer routing option (all events sent by default, filtered downstream with EventBridge rules).

### When to Use Them
- Real-time processing of newly uploaded files (e.g., image thumbnailing).
- Asynchronous ETL pipelines triggered on object arrival.
- Decoupled microservices: object storage → event → worker.
- Simple pub/sub workflows with fan-out (SNS → multiple Lambdas/SQS).
- Lightweight, on-the-fly data validation or virus scanning.

### When Not to Use Them
- Strict ordering or exactly-once delivery under high throughput (>5,000 events/sec).
- Full, immutable audit trails of every bucket operation (use CloudTrail Lake).
- Cross-Region event routing (EventBridge has built-in cross-Region support).
- Complex event patterns/transformations before delivery (EventBridge rule engine).
- Guaranteed delivery retries beyond default Lambda/SQS DLQ limits.

### Setting Up via AWS Management Console
1. Navigate to the S3 console and select your bucket.
2. Go to **Properties** → **Event notifications** → **Create event notification**.
3. Enter a name for the notification.
4. Under **Event types**, choose one or more (e.g., all object create events).
5. (Optional) Add **Prefix**/**Suffix** filters to narrow which keys trigger events (e.g., `images/`, `.jpg`).
6. Under **Destination**, pick Lambda function, SQS queue, or SNS topic.
7. Select or enter the ARN of the destination resource.
8. Click **Save changes**.

### Setting Up via boto3

```python
import boto3

s3 = boto3.client('s3')

notification_config = {
    'LambdaFunctionConfigurations': [
        {
            'Id': 'ImageUploadTrigger',
            'LambdaFunctionArn': 'arn:aws:lambda:us-east-1:123456789012:function:ProcessImage',
            'Events': ['s3:ObjectCreated:Put'],
            'Filter': {
                'Key': {
                    'FilterRules': [
                        {'Name': 'prefix', 'Value': 'uploads/'},
                        {'Name': 'suffix', 'Value': '.jpg'}
                    ]
                }
            }
        }
    ]
}

s3.put_bucket_notification_configuration(
    Bucket='my-photo-bucket',
    NotificationConfiguration=notification_config
)

print("Notification configured successfully.")
```

### Best Practices & Pitfalls
- Design consumers to be **idempotent** — S3 may deliver duplicates.
- Attach a **dead-letter queue (DLQ)** for Lambda failures or undeliverable SQS messages.
- Monitor invocation metrics in CloudWatch (Errors, Throttles).
- Limit filter rules — buckets have a 1,000-rule maximum across all configurations.
- Ensure proper IAM permissions: `s3:PutBucketNotification` on the bucket; `lambda:InvokeFunction` if targeting Lambda.

## 18. Requester Pays Buckets

Normally, the **bucket owner** pays for all storage and data transfer costs. **Requester Pays** shifts the cost of **data transfer and request charges** (not storage) to the requester making the download/API call — useful for buckets hosting large public datasets shared with many external consumers.

### Key Points
- Storage costs always remain with the **bucket owner**.
- The **requester** pays for GET/data-retrieval and transfer costs — must authenticate with valid AWS credentials (anonymous requests are not allowed on Requester Pays buckets).
- Requesters must explicitly acknowledge they'll be charged by including the header `x-amz-request-payer: requester` in their API calls; otherwise, the request fails with `403 Access Denied`.

### Enabling It

```bash
aws s3api put-bucket-request-payment \
  --bucket my-bucket-name \
  --request-payment-configuration Payer=Requester
```

### When to Use
- Publicly sharing large datasets (research data, open data, ML training sets) without absorbing everyone's download costs.
- Distributing data to multiple partner accounts where each should be billed for its own usage.

### Limitations
- Bucket owner **cannot use anonymous requests** to access their own Requester Pays bucket in some contexts — must include the payer header themselves too.
- Not compatible with **static website hosting**.
- CloudTrail logging and analytics tools must be configured to include the payer header.

## 19. S3 with AWS Lambda

S3 and Lambda together form the backbone of many serverless, event-driven architectures.

### Common Patterns
- **Event-driven processing**: S3 `ObjectCreated` event → Lambda trigger → e.g., resize images, extract metadata, transcode video, validate/parse uploaded files, trigger virus scanning.
- **ETL pipelines**: File lands in a "raw" bucket → Lambda transforms it → writes to a "processed" bucket, often chained with Step Functions for multi-stage pipelines.
- **S3 Object Lambda**: Lambda transforms data **on the fly as it's returned** by a GET request, without creating new copies of data (see [Section 27](#27-s3-object-lambda)).

### How the Trigger Works
1. Configure an **S3 Event Notification** (or EventBridge rule) targeting a Lambda function.
2. S3 invokes the Lambda function **asynchronously**, passing an event payload with bucket name, object key, and event type.
3. Lambda reads the object via `GetObject` (needs `s3:GetObject` IAM permission) and processes it.

### Best Practices
- Grant Lambda's execution role **least-privilege** access (scope to specific bucket/prefix).
- Beware of **recursive triggers** (Lambda writing back to the same bucket/prefix that triggered it → infinite loop) — write outputs to a different bucket or prefix.
- Set Lambda **concurrency limits** to avoid S3 event bursts overwhelming downstream systems.
- Use a **DLQ** or **on-failure destination** for failed asynchronous invocations.
- For heavy/long processing, have Lambda enqueue to SQS instead of doing the work inline (mind the 15-minute Lambda timeout).

## 20. S3 with AWS Glue and Athena

S3 is the storage layer underneath most AWS-native **data lake** and **analytics** stacks; Glue and Athena let you catalog and query that data without moving it.

### AWS Glue
- **Glue Crawler**: scans S3 data (CSV, JSON, Parquet, ORC, etc.), infers schema, and populates the **Glue Data Catalog** (a central metastore, Hive-metastore compatible).
- **Glue ETL Jobs**: serverless Spark/Python jobs that read from S3, transform data, and write back to S3 (often converting to columnar formats like **Parquet** for performance/cost).
- **Glue Data Catalog** is shared across Athena, Redshift Spectrum, and EMR — define the schema once, query from many engines.

### Amazon Athena
- A **serverless, interactive query service** that runs standard SQL directly against data in S3 — no infrastructure to manage.
- Uses the **Glue Data Catalog** for table/schema definitions.
- Billed **per query, per TB scanned** — cost optimization matters:
  - Use **columnar formats** (Parquet/ORC) instead of CSV/JSON.
  - **Partition** data (e.g., by date: `s3://bucket/year=2024/month=01/`) so queries scan less data.
  - **Compress** files (Snappy, gzip) to reduce bytes scanned.

### Typical Data Lake Query Flow
1. Raw data lands in S3 (raw/bronze zone).
2. Glue Crawler catalogs it / Glue ETL job transforms it into partitioned Parquet (curated/silver-gold zone).
3. Athena (or Redshift Spectrum) queries the catalog directly against S3 — no data loading step required.

### Interview Points
- Athena/Glue means you get **schema-on-read** — no need to pre-load into a database.
- Partitioning + columnar format is the #1 cost/performance lever tested in interviews.
- Glue Crawlers can be **scheduled** or triggered on new S3 data arrival (via Lambda/EventBridge) to keep the catalog current.

## 21. S3 with CloudFront

**Amazon CloudFront** is AWS's CDN; pairing it with S3 is the standard pattern for fast, global content delivery (static websites, images, videos, software downloads).

### Why Use CloudFront in Front of S3?
- **Lower latency**: caches content at edge locations close to users worldwide.
- **Reduced load & cost on S3**: fewer direct GETs to the origin bucket; CloudFront data transfer OUT to internet is often cheaper than S3 data transfer OUT.
- **HTTPS with custom domains**: attach ACM certificates and custom domain names easily.
- **DDoS protection**: integrates with AWS Shield/WAF at the edge.

### Recommended Architecture: Origin Access Control (OAC)
- Keep the S3 bucket **fully private** (Block Public Access enabled) and use **Origin Access Control (OAC)** — the modern replacement for the legacy **Origin Access Identity (OAI)** — so only CloudFront can read from the bucket, via a bucket policy that grants access to the specific CloudFront distribution.
- Users can then only reach content through CloudFront's URLs, never by hitting the S3 bucket URL directly.

### Key Configuration Points
- **Cache behaviors / TTLs**: control how long CloudFront caches objects before re-checking S3.
- **Signed URLs / Signed Cookies**: restrict access to private content served through CloudFront (paid content, per-user access).
- **Origin Groups**: configure a failover origin (e.g., a secondary S3 bucket in another Region) for high availability.
- **Invalidations**: force CloudFront to fetch fresh content from S3 before the TTL expires (has a cost per invalidation path beyond the free tier).

### CloudFront vs Direct S3 Access

| Aspect | Direct S3 | S3 + CloudFront |
|---|---|---|
| Latency | Higher for distant users | Low — served from nearest edge |
| Cost at scale | Higher data transfer cost | Generally lower for high-traffic, cacheable content |
| Security | Public bucket or presigned URLs | Bucket can stay fully private (OAC) |
| Best for | Internal/low-traffic access, uploads | Public-facing, high-traffic, cacheable content |

## 22. S3 with Data Lake Architecture

S3 is the de facto standard **storage layer for data lakes** on AWS due to its durability, scalability, low cost, and native integration with the entire analytics ecosystem.

### Why S3 for a Data Lake?
- Decouples **storage from compute** — data sits in S3; multiple engines (Athena, EMR, Redshift Spectrum, SageMaker) can read the same data without duplicating it.
- Virtually unlimited, cheap storage; pay only for what you use plus tiered storage classes for cost optimization.
- Strong consistency and durability (11 nines) make it safe as a single source of truth.

### Typical Zone-Based Architecture
| Zone | Purpose |
|---|---|
| **Raw / Bronze** | Immutable landing zone for ingested data, as-is from source systems. |
| **Curated / Silver** | Cleaned, validated, deduplicated, often converted to Parquet/ORC. |
| **Consumption / Gold** | Aggregated, business-ready data for BI tools, ML features, or reporting. |

### Common Companion Services
- **AWS Glue** — cataloging and ETL (see [Section 20](#20-s3-with-aws-glue-and-athena)).
- **Amazon Athena / Redshift Spectrum** — SQL query engines directly over S3.
- **AWS Lake Formation** — centralizes fine-grained permissions (row/column-level security) on top of the Glue Catalog and S3, simplifying governance across many consumers.
- **Amazon EMR** — big-data processing (Spark, Hive, Presto) reading/writing S3 as its data store (often using **EMRFS**).
- **Kinesis Data Firehose** — streams data directly into S3 for near-real-time ingestion.

### Best Practices
- Partition data by a high-cardinality, query-relevant key (commonly date).
- Use **lifecycle policies** to age out raw data into cheaper storage classes over time.
- Use **Lake Formation** for centralized access control instead of managing dozens of bucket policies.
- Enable **S3 Inventory** and **Storage Lens** to track dataset growth and cost drivers.

## 23. S3 Access Logs

**S3 Server Access Logging** records detailed records for every request made to a bucket — who made the request, when, from where, what action, and the response — for security auditing and traffic analysis.

### How It Works
- You enable logging on a **source bucket** and specify a **target bucket** (and optional prefix) where log files are delivered.
- Logs are delivered on a **best-effort basis** (typically within a few hours) — not real-time, and not guaranteed delivery (unlike CloudTrail).
- Each log entry includes: requester, bucket name, request time, action, response status, error code, bytes sent, turnaround time, referrer, user agent, and more.

### Enabling It

**Console:** S3 → Bucket → Properties → Server access logging → Edit → Enable, choose target bucket/prefix.

**Requirements:**
- Target bucket must be in the **same Region** as the source bucket.
- Grant the S3 Log Delivery group **write permission** on the target bucket (via ACL or bucket policy).
- Avoid using the **same bucket** as both source and target (creates a logging loop and clutter) — use a dedicated logs bucket.

### S3 Access Logs vs CloudTrail Data Events

| Aspect | S3 Server Access Logs | CloudTrail Data Events |
|---|---|---|
| Delivery | Best-effort, delayed (~hours) | Near real-time |
| Guarantee | Not guaranteed | More reliable, auditable |
| Format | Fixed log file format | Structured JSON |
| Cost | Free (only storage cost of logs) | Charged per event logged |
| Use case | General traffic analysis, debugging | Security/compliance audit trail |

### Use Cases
- Auditing who accessed which objects and when.
- Debugging unexpected traffic patterns or costs.
- Security investigations (combined with Athena to query log files at scale).

## 24. CloudTrail Integration

Integrating **AWS CloudTrail with Amazon S3** is a common and powerful setup for **auditing and compliance**, allowing you to store and analyze logs of all API activity across your AWS account.

### How AWS CloudTrail and S3 Integration Works

**CloudTrail Overview**
- Records **API calls and events** made via AWS Console, SDKs, CLI, and services.
- Events include **who did what, when, and from where**.

**S3 Integration**
- CloudTrail delivers logs to an **S3 bucket** you specify.
- You can then:
  - Archive logs for compliance.
  - Analyze logs using Athena, Glue, or Redshift.
  - Trigger alerts or workflows using Lambda or EventBridge.

### Steps to Set Up CloudTrail with S3

**1. Create or Choose an S3 Bucket**
- Use an existing bucket or create a new one.
- Enable versioning and encryption (recommended).

**2. Create a CloudTrail Trail**
- Go to **CloudTrail → Trails → Create trail**.
- Choose:
  - **Management events** (read/write)
  - **Data events** (S3, Lambda, etc.) — e.g., logging every `GetObject`/`PutObject` on a specific bucket.
  - **Insights events** (unusual activity)
- Set the destination S3 bucket.

**3. Set Permissions**
CloudTrail needs permission to write to your S3 bucket. AWS auto-creates a policy like:

```json
{
  "Effect": "Allow",
  "Principal": { "Service": "cloudtrail.amazonaws.com" },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::your-bucket-name/AWSLogs/your-account-id/*",
  "Condition": {
    "StringEquals": { "s3:x-amz-acl": "bucket-owner-full-control" }
  }
}
```

**4. Verify Logs**
Logs will appear in the S3 bucket under:
```
/AWSLogs/<account-id>/CloudTrail/<region>/<year>/<month>/<day>/
```

### Analyzing CloudTrail Logs in S3
- Use **Amazon Athena** to query logs directly from S3.
- Use **AWS Glue** to catalog and transform logs.
- Use **Amazon Redshift** for deeper analytics.

### Monitoring and Alerts
- Use **CloudWatch Logs** integration for real-time monitoring.
- Set up **EventBridge rules** to trigger Lambda on specific events (e.g., unauthorized access, root account usage).

## 26. S3 Select

**S3 Select** lets you retrieve **only a subset of data** from an object (CSV, JSON, or Parquet) using simple SQL expressions, instead of downloading and filtering the entire object client-side.

### Why Use It?
- Reduces the amount of data transferred (up to 400% faster, up to 80% cost reduction, per AWS) by filtering **at the S3 layer**.
- Ideal for large CSV/JSON/Parquet files where an application only needs a few columns or rows.

### Example

```python
import boto3

s3 = boto3.client('s3')

response = s3.select_object_content(
    Bucket='my-bucket',
    Key='data/sales.csv',
    ExpressionType='SQL',
    Expression="SELECT s.region, s.amount FROM s3object s WHERE s.amount > 1000",
    InputSerialization={'CSV': {'FileHeaderInfo': 'USE'}},
    OutputSerialization={'CSV': {}}
)

for event in response['Payload']:
    if 'Records' in event:
        print(event['Records']['Payload'].decode('utf-8'))
```

### Limitations
- Supports a **subset of SQL** (no joins, limited functions).
- Input formats: CSV, JSON, Parquet (optionally compressed with gzip/bzip2).
- Best suited for simple filter/project queries — for complex analytics, use **Athena** instead (which is actually built on similar underlying tech but supports full SQL and joins across many files).

### S3 Select vs Athena

| Aspect | S3 Select | Athena |
|---|---|---|
| Scope | Single object | Entire table/dataset (many files) |
| SQL support | Basic (filter/project) | Full ANSI SQL, joins, aggregations |
| Use case | App-level, per-request filtering | Ad-hoc analytics across a dataset |

## 27. S3 Object Lambda

**S3 Object Lambda** lets you add your own code (a Lambda function) to **process data as it is returned** by a standard S3 GET request — **without creating or storing additional copies** of the data.

### How It Works
1. Create a Lambda function that receives the original object and transforms it.
2. Create an **S3 Object Lambda Access Point**, associated with a standard S3 Access Point and your Lambda function.
3. Applications call `GetObject` on the **Object Lambda Access Point** ARN instead of the bucket directly.
4. S3 automatically invokes your Lambda, which fetches the original object, transforms it, and returns the modified data to the caller.

### Use Cases
- **Redacting sensitive data** (PII masking) for different consumers of the same underlying object.
- **Resizing images on the fly** for different client needs, without storing every variant.
- **Converting formats** (e.g., XML → JSON) at request time.
- **Enriching data** by combining the S3 object with data from another source before returning it.
- **Watermarking** or applying access-based content variations.

### Key Points
- Only supports `GetObject`, `HeadObject`, and `ListObjects` (as of general availability) — not a general write-side transform.
- No need to store multiple derivative copies of the same object → saves storage cost.
- Adds Lambda invocation latency/cost per request — not ideal for extremely high-throughput, low-latency read paths.

## 28. S3 Inventory

**S3 Inventory** provides a scheduled, flat-file report (CSV, ORC, or Parquet) listing your objects and their metadata — an alternative to using the `ListObjects` API to audit large buckets, which can be slow and costly at scale.

### Why Use It?
- Auditing buckets with **millions/billions of objects** where `ListObjectsV2` calls would be slow and expensive.
- Feeding downstream systems (Athena, Glue) for **cost analysis, compliance checks, or data cataloging**.
- Verifying **replication and encryption status** of every object without a live API scan.

### Configuration
- Delivered daily or weekly to a destination bucket you specify.
- Configurable fields include: size, last modified date, storage class, ETag, encryption status, replication status, Object Lock retention, and more.
- Can be scoped to the whole bucket or filtered by prefix.

### Example Fields in an Inventory Report
```
Bucket, Key, Size, LastModifiedDate, ETag, StorageClass,
IsMultipartUploaded, ReplicationStatus, EncryptionStatus,
ObjectLockRetainUntilDate, ObjectLockMode
```

### Use Cases
- Feed an Athena table over the inventory report to run SQL audits ("find all unencrypted objects", "find objects not replicated").
- Drive **S3 Batch Operations** jobs (inventory reports are a common input "manifest").
- Track storage class distribution over time for cost optimization.

## 29. S3 Batch Operations

**S3 Batch Operations** lets you perform a single operation across **billions of objects** with one request — instead of writing custom scripts to loop through objects.

### Supported Operations
- Copy objects (e.g., to another bucket/Region).
- Invoke a **Lambda function** on each object (fully custom logic).
- Replace all object tags.
- Replace access control lists (ACLs).
- Restore objects from Glacier/Deep Archive at scale.
- Apply **Object Lock** retention or legal hold at scale.
- Encrypt objects that are currently unencrypted.

### How It Works
1. Provide a **manifest** — a list of objects to act on. This can be:
   - A CSV file you provide.
   - An **S3 Inventory report** (most common approach).
   - Output from an **S3 Select** query.
2. Choose the **operation** to perform and its parameters.
3. Submit the **Batch Operations job**; S3 processes it (retrying failures automatically) and produces a **completion report**.
4. Requires an **IAM role** with permission to perform the target operation and read the manifest.

### Use Cases
- Migrating **billions of objects** to a new storage class or encryption setting after a compliance change.
- Bulk-restoring millions of Glacier objects for a one-time analytics job.
- Applying a new tagging scheme across an entire legacy bucket.
- Running a custom Lambda transformation (e.g., re-encoding images) across an entire dataset.

### Key Points
- Designed for **massive scale** (billions of objects) where per-object API calls would be impractical.
- Automatically **retries failed operations** and gives you a detailed **completion report** (successes/failures per object).
- Much cheaper and more reliable than a custom script looping through `ListObjectsV2` + per-object API calls.

## 30. Presigned URLs

A **presigned URL** grants **temporary, time-limited access** to a private S3 object (upload or download) without requiring the requester to have AWS credentials or IAM permissions of their own.

### How It Works
- Generated by someone who **does** have valid credentials/permissions (e.g., your backend server), using the AWS SDK.
- The URL embeds a signature (derived from the requester's credentials, expiration time, and the request) that S3 validates on access.
- Anyone holding the URL can perform the specified action (GET or PUT) **until it expires** — max expiration is 7 days when using IAM user/role credentials with SigV4 (unless using temporary STS credentials, which are further capped by the credential's own expiration).

### Example (Python / boto3)

```python
import boto3

s3 = boto3.client('s3')

url = s3.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'my-bucket', 'Key': 'private/report.pdf'},
    ExpiresIn=3600  # 1 hour
)
```

### Common Use Cases
- Letting users **upload files directly to S3** from a browser/mobile app, without routing large files through your backend.
- Sharing a **private file temporarily** (e.g., a generated invoice or report) without making the bucket/object public.
- Time-boxed access to downloadable content (e.g., a purchased e-book link).

### Key Points
- The URL is only as secure as the **expiration time** and where it's shared — treat it like a temporary password.
- Presigned URLs **inherit the permissions of the credentials used to generate them** — if that IAM identity loses access, the presigned URL stops working too.
- Can be generated for both `GetObject` (download) and `PutObject` (upload).

## 31. Static Website Hosting

S3 can host a **static website** (HTML/CSS/JS, no server-side code) directly from a bucket.

### Setup
1. Enable **Static website hosting** on the bucket (Properties tab), specify an **index document** (e.g., `index.html`) and optional **error document** (e.g., `error.html`).
2. Make the bucket content **publicly readable** — requires disabling Block Public Access (at least the relevant setting) and attaching a bucket policy granting `s3:GetObject` to `*`.
3. Website is served over HTTP at an endpoint like:
   `http://<bucket-name>.s3-website-<region>.amazonaws.com`

### Important Limitations
- **No native HTTPS** on the S3 website endpoint — you must put **CloudFront** in front for TLS/custom domains (see [Section 21](#21-s3-with-cloudfront)).
- Not compatible with **Requester Pays**.
- No server-side processing — purely static assets (though JS can call external APIs, e.g., API Gateway/Lambda, for dynamic behavior).

### Recommended Production Pattern
- S3 (private bucket, Object Lock/versioning optional) → CloudFront (with OAC, ACM cert for HTTPS, custom domain via Route 53) → end users.
- This avoids the HTTP-only limitation and improves performance/security versus using the raw S3 website endpoint.

## 32. S3 Access Points

**S3 Access Points** are named network endpoints attached to a bucket that simplify managing access for shared datasets with many different applications/teams, each needing distinct permissions.

### Why Use Access Points?
- Instead of one large, complex bucket policy trying to handle every consumer's access pattern, you create a **separate access point per application/team**, each with its own policy and (optionally) its own restricted network origin (e.g., a specific VPC).
- Simplifies auditing — each access point's policy is scoped and easier to reason about than one giant bucket policy.

### Key Features
- Each access point has its own **DNS name** and **ARN**; applications use the access point's ARN/hostname to access the bucket's data instead of the bucket directly.
- Can restrict an access point to only be reachable from a specific **VPC** (`VpcConfiguration`), enforcing network-level isolation.
- Supports the same permission constructs (policy, block public access settings) scoped to that access point.
- **Multi-Region Access Points**: a single global endpoint that routes requests to the closest replica bucket across Regions — useful for global applications needing low-latency access to replicated data.

### Use Cases
- A shared data lake bucket accessed by multiple teams, each via their own access point with tailored permissions.
- Enforcing that a particular application can only reach S3 from within its own VPC.
- Simplifying migration/refactors by fronting a bucket with multiple access points instead of restructuring bucket policies each time a new consumer is added.

## 33. S3 Storage Lens

**S3 Storage Lens** provides organization-wide visibility into **object storage usage and activity trends**, with recommendations for cost optimization and data protection best practices.

### Key Features
- **Default dashboard** (free) — aggregated metrics across all buckets/accounts in an AWS Organization.
- **Advanced metrics & recommendations** (paid tier) — activity metrics (requests, bytes uploaded/downloaded), detailed status metrics (encryption, versioning, replication status per bucket), and **28 days of historical data** plus exportable raw metrics to another S3 bucket.
- Contextual recommendations, e.g., flagging buckets without lifecycle policies, encryption, or versioning enabled.

### Use Cases
- Enterprise-wide cost and usage governance across hundreds of accounts/buckets.
- Identifying buckets that are candidates for **Intelligent-Tiering** or lifecycle policies based on actual access patterns.
- Spotting buckets missing security best practices (no encryption, public access, no versioning) at scale.

## 34. Common Interview Questions

A quick-reference set of frequently asked S3 interview questions, mapped to the section that answers them:

1. **What's the difference between S3 and EBS/EFS?** → Object storage (flat namespace, HTTP API, no OS mount) vs. block storage (EBS, attached to one EC2 instance) vs. file storage (EFS, POSIX, mountable by many instances).
2. **How does S3 achieve 11 nines of durability?** → Data is redundantly stored across ≥3 Availability Zones ([Section 1](#1-what-is-s3)).
3. **Bucket policy vs IAM policy vs ACL — when do you use each?** → [Sections 5–7](#5-bucket-policies).
4. **How do you make a bucket private but still let a Lambda/EC2 instance access it?** → IAM role + bucket policy scoped to that role/VPC endpoint ([Sections 6, 10](#6-iam-policies-for-s3)).
5. **How do you serve private content securely to end users?** → Presigned URLs, or CloudFront with signed URLs/cookies ([Sections 21, 30](#21-s3-with-cloudfront)).
6. **How do you upload a 10 GB file reliably?** → Multipart upload with retry logic per part ([Section 15](#15-multipart-uploads)).
7. **How do you reduce storage cost for old logs?** → Lifecycle rules transitioning to IA → Glacier → Deep Archive ([Section 11](#11-lifecycle-policies)).
8. **How do you protect objects from accidental/malicious deletion?** → Versioning + MFA Delete + Object Lock (Compliance mode) ([Sections 12–13](#12-object-locking-and-retention)).
9. **How do you process files as soon as they're uploaded?** → S3 Event Notification → Lambda/SQS/SNS ([Sections 17, 19](#17-event-notifications)).
10. **How do you query data in S3 without loading it into a database?** → Athena + Glue Data Catalog, or S3 Select for single-object queries ([Sections 20, 26](#20-s3-with-aws-glue-and-athena)).
11. **What happens if two clients PUT the same key at the same time?** → Last writer wins; with strong consistency, subsequent reads see the latest successful write ([Section 4](#4-data-consistency-model)).
12. **How do you audit who accessed an object?** → S3 Server Access Logs and/or CloudTrail data events ([Sections 23–24](#23-s3-access-logs)).
13. **How do you avoid paying for orphaned multipart uploads?** → Lifecycle rule `AbortIncompleteMultipartUpload` ([Section 11](#11-lifecycle-policies)).
14. **How would you architect a low-latency global data lake?** → S3 (zoned raw/curated/consumption) + Glue Catalog + Athena/Redshift Spectrum + Lake Formation for governance ([Section 22](#22-s3-with-data-lake-architecture)).
